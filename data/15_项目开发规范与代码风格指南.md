# 项目开发规范与代码风格指南

## 1. Python 编码规范

### 1.1 代码风格
遵循 PEP 8 编码规范，核心要求如下：
- 缩进：使用 4 个空格，不使用 Tab
- 行长度：不超过 88 个字符（兼容 Black 格式化工具）
- 空行：顶层函数和类定义前后各空两行，类内方法定义前后各空一行
- 导入顺序：标准库 > 第三方库 > 本地模块，每组之间空一行

### 1.2 命名规范
| 类型 | 命名规则 | 示例 |
|-----|---------|------|
| 类名 | PascalCase | `MedicalImageProcessor` |
| 函数/方法 | snake_case | `load_dicom_file()` |
| 变量 | snake_case | `image_shape` |
| 常量 | UPPER_CASE | `MAX_IMAGE_SIZE` |
| 私有属性 | _snake_case | `_internal_cache` |

### 1.3 类型注解
所有函数参数和返回值必须添加类型注解：
```python
def process_image(
    file_path: str,
    resize_to: tuple[int, int]
) -> np.ndarray:
    ...
```

## 2. Git 提交流程

### 2.1 分支命名
- 功能分支：`feature/功能描述-日期`
- 修复分支：`fix/问题描述-日期`
- 发布分支：`release/v版本号`

### 2.2 Commit Message 规范
采用 Conventional Commits 规范：
```
<type>[optional scope]: <description>

[optional body]
[optional footer]
```
类型包括：feat、fix、docs、style、refactor、test、chore

### 2.3 Code Review 要求
所有合并到 main 分支的代码需经过至少 1 人 Code Review，重点检查：
- 逻辑正确性（是否存在边界条件遗漏）
- 性能效率（是否存在不必要的计算或重复代码）
- 安全性（是否存在 SQL 注入、路径穿越等风险）
- 可测试性（代码是否易于编写单元测试）

## 3. 测试要求

### 3.1 单元测试覆盖
新功能代码的单元测试覆盖率不低于 80%，使用 pytest 框架编写测试用例。

### 3.2 测试文件命名
测试文件命名规则：`test_<模块名>.py`，测试函数命名：`test_<功能描述>_<场景>`。

## 4. 文档要求

每个模块必须包含模块级别的 docstring，说明模块功能、主要类和函数。API 接口必须包含 Swagger/OpenAPI 注释。
